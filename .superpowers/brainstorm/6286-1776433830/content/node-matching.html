DOM ↔ View 节点匹配策略

设计稿层次 vs 代码层次不一定 1-1 对应，哪种策略更鲁棒？

核心问题：设计稿 1 个节点 → 代码可能是 N 个 View 的组合
例如设计稿里一个「带图标的按钮」是 1 个 div，Android 实现是 LinearLayout + ImageView + TextView 三层。
靠结构匹配会失败，靠 id 精确匹配也无法覆盖所有中间容器层。
设计稿 DOM
div.card
div.btn-icon ← 锚定目标
img.icon
span.label
⟷
Android View 树
FrameLayout
LinearLayout (容器，无对应)
LinearLayout (btn) ← 真正对应
ImageView
TextView

A. 纯 id 约定

  • ✅ 精确，零歧义
  • ✅ 可忽略中间容器
  • ❌ AI 写代码必须严格遵守命名规范
  • ❌ 容器层无对应 id，覆盖不完整
  • ❌ 规范一旦不一致全部失效

B. 纯坐标匹配

  • ✅ 不依赖命名规范
  • ❌ 层次不对应时，多个 View 包围同一坐标区域
  • ❌ 容器 View 和叶子 View 坐标重叠，歧义大
  • ❌ 无法区分「哪一层才是需要核对的那个」
★ 推荐

C. 叶子节点 + 坐标

  • ✅ 只匹配「叶子节点」（最终渲染单元）
  • ✅ 设计稿叶子 ↔ View 叶子，层次差异自动消除
  • ✅ 用坐标 + 类型辅助区分歧义
  • ✅ 对中间容器不做核对，只核对可见内容
  • ❌ 纯容器的 padding/margin 问题需额外处理
推荐方案：叶子节点匹配 + 类型辅助
只核对最终渲染的叶子节点（TextView、ImageView、可见 div），不强求层次一致。
匹配规则：相同类型（text↔TextView, img↔ImageView）+ 锚点相对坐标最近 → 即为同一元素。
id 作为可选的精确覆盖（有 id 优先用，没有降级用坐标），不作为唯一依赖。
